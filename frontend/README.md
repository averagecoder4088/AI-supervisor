# Order Supervisor: frontend

Next.js (App Router) + TypeScript + Tailwind CSS. The UI for the Order Supervisor backend: create supervisors, start runs, inject events, add run-specific instructions, use the human controls (pause, resume, interrupt, terminate) and observe a run (workflow status, memory, timeline, actions, tool executions, final output), with live updates while a run is active.

For the whole system (architecture, diagrams, setup of PostgreSQL, Temporal, the worker and the backend) see the [root README](../README.md). This file only covers the frontend.

## Run it

The backend, its worker and Temporal must be running first (see the root README, "Running the application").

```bash
cd frontend
npm install
npm run dev            # http://localhost:3000
```

Production build: `npm run build && npm start`. Checks: `npm run lint` and `npx tsc --noEmit`.

Note: the Next.js 16 development server writes `AGENTS.md` and `CLAUDE.md` into this directory on first start. They are generated by Next.js, are not part of the project and can be deleted.

## Configuration

| Variable | Default | Meaning |
|---|---|---|
| `API_BASE_URL` | `http://127.0.0.1:8000` | Base URL of the FastAPI backend. Server-side only. |

Copy `.env.example` to `.env.local` to override it. Every backend call runs on the Next.js server (Server Components for reads, Server Actions for writes), so the browser never contacts the backend directly and no CORS setup is needed.

## Routes

| Route | Shows |
|---|---|
| `/` | Dashboard: *Active runs* and *Completed and ended runs*, with a **Run status** column (the application's record; a paused supervisor still reads `running`) and buttons to create a supervisor or start a run |
| `/supervisors` | Supervisors referenced by existing runs (read-only; the backend has no supervisor-list endpoint) |
| `/supervisors/new` | Create a supervisor (tools, wake behaviour, terminal statuses, event to status mapping) |
| `/runs/new` | Start a run: order ID, supervisor, run-specific instructions |
| `/runs/[runId]` | The run page, top to bottom: **Run overview** (header shows the run status and the live workflow state), **Workflow status**, **Human controls**, **Instructions** (base instruction plus additional run instructions and a form to add one), **Inject an event**, then the observation sections **Memory**, **Timeline**, **Actions**, **Tool executions** and **Final output**. For a run that is no longer active the controls and forms give way to a short explanation. |

Each observation section loads on its own, so one failing source shows "unavailable" without breaking the page.

## Live updates

While a run is active, `src/components/LiveRefresh.tsx` calls `router.refresh()` every 3 seconds, which re-runs the Server Components (the browser never calls the observation endpoints itself). The same component owns the **Refresh** button, so an automatic and a manual refresh can never overlap. Polling continues while the workflow is paused, skips a hidden tab, and stops when the run is completed, terminated or failed, or when the workflow is reported closed on two consecutive renders. A failing status query or an unreachable backend does not stop it. The settings are in `src/polling.ts` (`POLL_INTERVAL_MS`, `CLOSED_CONFIRMATIONS`, and `STATUS_READ_TIMEOUT_MS`, which caps the workflow-status read at 3 seconds so a dead Temporal cannot make every refresh slow). There are no WebSockets or server-sent events.

## Backend endpoints used

`GET /api/runs`, `GET /api/runs/{run_id}`, `GET /api/supervisors/{supervisor_id}`, `POST /api/supervisors`, `POST /api/runs`, `POST /api/runs/{run_id}/events`, `POST /api/runs/{run_id}/instructions`, `GET /api/runs/{run_id}/status`, `GET /api/runs/{run_id}/timeline|memory|actions|tool-executions|final-output`, `POST /api/runs/{run_id}/pause|resume|interrupt|terminate`. All calls live in `src/api/`.

## How the browser writes to the backend

The backend has no CORS configuration, so the browser never calls it. The forms use React form actions backed by Next.js **Server Actions** (`src/app/supervisors/new/actions.ts`, `src/app/runs/new/actions.ts`, `src/app/runs/[runId]/actions.ts`): the browser posts to the Next.js server, and the action calls FastAPI from there. Validation stays authoritative in the backend; the forms only catch obvious mistakes early. Backend errors are turned into readable messages (`src/api/messages.ts`), and the submit buttons are disabled while a request is in flight.

Creating a supervisor with an existing name creates the next *version* (versions are immutable). A run that failed to start keeps its order ID, so retrying the same order ID reports "already exists" (existing backend behaviour).

## Source layout

```
src/
  app/            App Router pages (dashboard, supervisors, runs); runs/[runId]/ holds the run page,
                  its Server Actions, the human controls and the observation sections
  api/            the only code that talks HTTP to the backend, error messages, types, vocabularies
  components/     shared UI: badges, form pieces, LiveRefresh
  polling.ts      polling settings
  format.ts       timestamp formatting
```

## Tests

The frontend has no automated test suite of its own. It is checked with lint, the TypeScript compiler and a production build, and its flows were exercised in a real browser against the real backend stack.
