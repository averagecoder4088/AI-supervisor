Order Supervisor, explained from zero

A step-by-step guide to how the project works: the parts, the workflow, the rules, and why each choice was made. One running example throughout: order A-1001.

1. What is this project?

Imagine you ship an online order. Things happen to it over days: payment is confirmed, the parcel is shipped, it gets delayed, the customer writes in, it is finally delivered. Someone has to keep an eye on that order and react at the right moments.

Order Supervisor is that someone, built as software. For every order it starts one long-running supervisor. The supervisor sleeps most of the time, wakes up when something important happens (or when a timer fires), thinks using an AI model, and may take one action such as sending the customer a message. When the order reaches a final state such as delivered, it writes a summary and stops.

In plain words

Think of a night-shift manager who is responsible for one parcel. They nap, but a phone alert wakes them for big news. They can read a note pad (memory), ask an advisor (the AI) what to do, and then do at most one thing. You can tell them to pause, resume, or stop.

Long-running

One supervisor lives for the whole life of an order: hours or days, not milliseconds.

Durable

If the server restarts, the supervisor picks up where it stopped. Temporal guarantees that.

Careful

The AI only suggests. Ordinary code checks the suggestion and does the action.

Watch out

The workflow is deterministic: no clock reads, no random numbers, no network calls inside it. Temporal replays workflow code from history to recover, and that only works if the same history always produces the same steps. That is why every outside action lives in an Activity.

People mix these up, so it is worth being exact.

  • The Run is a database row. Its status is one of starting, running, completed, terminated, failed.
  • The Workflow is the live supervisor inside Temporal. Its state is sleeping, reasoning, paused or terminal.
  • Paused exists only in the workflow. A paused run still says running in the database.
  • There is exactly one workflow per order, and its id is always order-{order_id}, for example order-A-1001.

4. Starting a run

You first create a supervisor: a reusable template that holds the base instructions, which tools are allowed, which events count as important, wake intervals, and which order statuses are final. Then you start a run for one order using that supervisor.

sequenceDiagram
    participant U as You
    participant N as Next.js
    participant A as FastAPI
    participant P as PostgreSQL
    participant T as Temporal
    participant W as Worker
    U->>N: Start run for order A-1001
    N->>A: POST /api/runs
    A->>P: save run, status starting
    A->>T: start_workflow, id order-A-1001
    T-->>A: started
    A->>P: set run status running
    A-->>N: 201 Created
    T->>W: run OrderWorkflow
    W->>W: initialize state and config
    W->>W: first reasoning pass, reason: workflow start

The important rules of starting

  • One start path. Only POST /api/runs ever starts a workflow, by calling start_workflow once.
  • No Signal-With-Start. Temporal has a feature that starts a workflow and sends it a message in one call. This project does not use it. Events and controls only go to a workflow that already exists.
  • Safe initial state. The workflow sets up its configuration in a special constructor (@workflow.init) before any message can be handled. So even a message that arrives at the very first moment sees a fully prepared workflow.
  • Two systems, not one transaction. PostgreSQL and Temporal cannot commit together. So the run row is saved as starting first, and only after Temporal accepts is it set to running (or failed).
Example

You send an event to a run that does not exist or already finished. The API answers 409 RUN_NOT_ACTIVE. It never quietly starts a new workflow for you.

In plain words

Messages (Signals) never do heavy work themselves. When one arrives, the workflow just writes it on a to-do list and maybe sets a "wake up" flag. The loop then saves the list to the database and decides whether to think.

6. What wakes the supervisor

Not every event should cost an AI call. There are exactly five things that can start a reasoning cycle.

Example

For order A-1001, the events order_created, payment_confirmed and shipment_created arrive. None is on the important list, so all three are saved to the timeline and nothing else happens: no AI cost. Then shipment_delayed arrives. It is important, so the supervisor wakes and thinks. The unimportant events are handed to the AI at that moment as "new events".

Two small details: while a wake is already queued, another wake does not stack on top of it. And while the supervisor is paused, events are still recorded but nothing wakes it.

7. One reasoning cycle

When the supervisor wakes up, it runs one reasoning cycle. This is the heart of the project.

sequenceDiagram
    participant W as Workflow
    participant R as Reasoning Activity
    participant L as LLM
    participant X as Tool Activity
    participant D as PostgreSQL
    W->>R: memory, new events, instructions, allowed tools
    R->>L: prompt asking for JSON only
    L-->>R: decision as JSON
    R-->>W: validated decision
    W->>W: checkpoint: interrupted? paused? terminal?
    W->>W: validate tool, inputs and wake time
    W->>D: record action started
    W->>X: run the one tool
    X-->>W: tool result
    W->>D: record action finished
    W->>D: save memory snapshot
    W->>W: schedule next wake

What the AI receives and returns

Receives

Compact memory, new and recent events, the supervisor's instructions, this run's extra instructions, the enabled tools, and the last action result. It never sees the whole database.

Returns (JSON)

An assessment, an optional single tool with its input, when to wake next (in minutes), and a memory update (a summary and open concerns).

{
  "assessment": "Shipment is delayed. Customer may worry.",
  "tool": "send_customer_update",
  "tool_input": { "message": "Your parcel is delayed by a day. Sorry!" },
  "next_wake_in_minutes": 45,
  "memory_update": {
    "situation_summary": "Delay reported; customer informed.",
    "open_concerns": ["confirm new delivery date"]
  }
}

Why the workflow does not just trust the AI

  • Checkpoint. Things may have changed while the AI was thinking. If you pressed Interrupt or Pause, or the order became final, the decision is discarded: no tool runs.
  • Validation. The tool must exist, be enabled for this supervisor, and have its required inputs. Only one tool is ever allowed. The wake time is clamped between the supervisor's minimum and maximum.
  • Only Activities act. Even a valid decision is carried out by a tool Activity, never by the AI.
Example

The AI asks for escalate_shipment, but this supervisor only enabled send_customer_update. The workflow rejects it, writes "Tool request rejected" on the timeline, and still saves the memory update and schedules the next wake.

"Nothing applied" means

A discarded decision or a failed AI call runs no tool, saves no memory snapshot, and leaves new events waiting. The workflow only records the outcome and a note on the timeline, then schedules the next wake (or stays paused). It does not end the workflow.

8. Events: how news reaches the supervisor

An event is a fact about the order: payment_confirmed, shipment_delayed, delivered. In a demo, an operator or a simulator sends them.

sequenceDiagram
    participant U as Operator
    participant A as FastAPI
    participant T as Temporal
    participant W as Workflow
    participant D as PostgreSQL
    U->>A: POST /api/runs/id/events
    A->>T: Signal submit_event
    A-->>U: 202 Accepted
    T->>W: deliver Signal
    W->>W: queue record, update order status if mapped, maybe set wake
    W->>D: main loop saves event and timeline entry
  • 202 means "accepted by the workflow", not "already saved". The workflow saves it a moment later.
  • Every event is saved, whether or not it wakes the AI.
  • A supervisor can map an event to an order status. For example delivered maps to the status delivered. If that status is on the supervisor's "final" list, the run ends.
  • If the workflow is busy thinking, new events wait in a queue and are saved when the loop reaches its next save step.

9. Human controls

Four buttons on the run page let a person steer the supervisor. Three are Temporal Signals (messages to the running workflow). One is not.

ControlHow it is sentWhat it doesWorkflow alive?
PauseSignalStops reasoning and suspends the timer. Events are still recorded.yes
ResumeSignalEnds the pause and wakes the supervisor to look at everything that piled up.yes
InterruptSignalAbandons an in-flight AI call and clears any queued wake. A tool that is already running is not cancelled.yes
TerminateTemporal client hard stop (not a Signal)Kills the workflow at once. The API then records the run as terminated.no
Example

The AI is thinking about A-1001 and is about to send the customer a message. You press Pause. When the AI's answer arrives, the checkpoint sees "paused" and discards it, so no message goes out. Later you press Resume: the supervisor wakes, sees the events that arrived during the pause, and thinks again.

Why terminate is different

Terminate is a hard stop that workflow code cannot intercept, so it does not clean up: no final output is produced, and unsaved queued records are lost. Use Pause or Interrupt for gentle control.

10. How a run ends

A run ends when the order's status reaches one of the supervisor's configured terminal statuses (for example delivered or cancelled). This is decided by a simple rule on incoming events, not by the AI.

flowchart TB
    t["Terminal status reached
not an LLM decision"] --> f1["Flush queued records"]
    f1 --> fo["Final output
LLM, or deterministic fallback"]
    fo --> f2["Flush late records"]
    f2 --> cr["complete_run Activity
saves final output, run = completed"]
    cr --> dr["Final drain
persist any late Signals"]
    dr --> e(["Workflow ends"])

    classDef term fill:#cffafe,stroke:#0891b2,color:#111
    classDef step fill:#ffffff,stroke:#94a3b8,color:#111
    class t,f1,fo,f2,cr,dr term
    class e step
  • Reasoning never restarts after this point. Late events, instructions and controls are still saved, but they cannot reopen the workflow.
  • If the AI cannot write the final summary, a deterministic fallback builds one from what was recorded. Its output is tagged source: fallback, otherwise source: llm.
  • If the order becomes final while the AI is mid-thought, that decision is discarded and the workflow goes straight to this path.

In plain words

Temporal holds the supervisor's live state (what it is doing right now). PostgreSQL holds the record of what happened, so the website can show history. The workflow does not read from PostgreSQL to make decisions; it keeps a compact memory of its own.

12. Failures and safety

Things go wrong. Here is what the design does about each.

What goes wrongWhat the system does
The AI is down or returns bad JSONTemporal retries the call (up to 3 attempts). If it still fails, the cycle ends with "no tool executed", the workflow stays alive, and it tries again at the next wake.
The AI suggests a wrong or disabled toolThe workflow rejects it and notes why on the timeline.
A tool that only reads crashesRetried (up to 3 attempts), because repeating a read is harmless.
A tool with side effects crashesOne attempt only. A retry could send the customer a second message. The failure is recorded instead.
Saving to the database fails brieflyRetried (up to 5 attempts). Saves are idempotent: ids are made by the workflow and inserts use "do nothing if exists", so a retry never creates duplicates.
The worker or server restartsTemporal replays the workflow from history and it continues.
You send an event to a finished run409 RUN_NOT_ACTIVE. Nothing is started.
Temporal is unreachableThe API answers 503 TEMPORAL_UNAVAILABLE; database-only pages still work.

Known limits (a proof-of-concept, honestly stated)

A final safety audit found no critical or high blockers. It did list three medium limits:
  • M1. A control signal that lands in the tiny gap between the checkpoint and the tool starting will not stop that one already-validated tool.
  • M2. If the database is down long enough to exhaust retries, the workflow fails and the run row can stay running. Nothing reconciles it automatically.
  • M3. If start_workflow times out in an ambiguous way, a workflow could in theory be running while the run is marked failed. Rare.

Other stated limits: no Continue-As-New, the mock tables are not auto-created, and the UI re-renders the whole page every 3 seconds.

This follows the tested "delayed shipment" scenario. The supervisor treats shipment_delayed and customer_message_received as important.

17. Glossary

TermMeaning
WorkflowDurable code that Temporal keeps alive and replays after a crash. Here: OrderWorkflow.
ActivityA function that does real work (database, AI, tool). Can be retried.
SignalA message sent to a running workflow. Changes state, returns nothing.
QueryA read-only question to a running workflow, such as get_status.
WorkerThe process that runs workflow and Activity code for Temporal.
Task queueThe named line the worker takes work from. Here: order-supervisor.
DeterminismThe workflow must do the same steps every time it is replayed from history.
IdempotentDoing it twice has the same result as doing it once.
Wake reasonWhy the supervisor started thinking: workflow start, important event, scheduled wake-up, resume, or instruction added.
CheckpointThe check after the AI answers: interrupted? paused? terminal? If yes, discard the decision.
Terminal statusA final order status (for example delivered) that ends the run.
SupervisorA reusable template: instructions, tools, important events, wake times, terminal statuses.
RunOne supervised order: a database row plus one live workflow.
Signal-With-StartA Temporal feature that starts a workflow and signals it at once. Not used by this project.
If you remember only five things
  1. One long-lived Temporal workflow per order, id order-{order_id}.
  2. The AI only returns JSON. Workflow rules check it, and Activities do the work.
  3. Five triggers wake the AI; unimportant events are recorded without waking it.
  4. At most one tool per cycle. Tools with side effects get one attempt.
  5. The run ends by a status rule, then: flush, final output, complete_run, drain, end.
